Proof-carrying debugging for Python

Most tools guess.
Buggy executes, then proves.

Buggy runs your function against the inputs most likely to break it. When one does, it verifies the failure three separate ways before calling it a bug — then proposes fixes and verifies each one by running it. It never edits your code on its own.

The gap Buggy fills

Static analysis tells you where a bug might be. AI assistants write a fix that looks right. Neither one proves anything, and both hand you the triage work.

The usual loop

  • A warning fires on a line that execution may never reach.
  • You read the code to decide whether it is real. That is the expensive part.
  • A patch lands, the suite goes green, production finds the edge case.
  • Nothing checked whether the fix generalises past the example that caught it.

With Buggy

  • A concrete input is produced that actually breaks the function.
  • The failure is re-run and re-checked before it is reported at all.
  • Fixes are derived from the failing input, not from a generic template.
  • Every fix is applied and executed, so the verdict rests on behaviour.
Three statuses, kept apart on purpose. proven means a failing input survived all three checks. unconfirmed means nothing failed within the budget, which is not a proof of safety. no_valid_input means the preconditions rejected every candidate, so the function never ran and nothing was learned. Collapsing the last two into a pass is how a tool starts lying to you.

Four steps, run in order

Each step maps to a command you can run on its own. Nothing is hidden behind an orchestrator, and nothing is written to your files at any point.

Inspect — see what is there without running it

buggy functions reads the file with Python's own ast and reports every function, its signature, and whether it can be investigated — and if not, why. Parsing only: your module is never imported, so nothing it does at import time happens. Start here on code you do not know.

  • Standard-library ast
  • No execution at all
  • Signature and annotation reading
  • Says why something was skipped

Prove — find a real failing input, then distrust it

The generator tries the values that break arithmetic first — 0, nan, ±inf, huge integers, empty collections, empty strings — before anything random. Candidates run in a reusable worker process at about 0.015 ms per call, and a violation only becomes a certificate after admissibility, soundness and reproducibility all pass.

  • Edge cases before randoms
  • Real execution, not simulation
  • Timeout · crash · postcondition · non-finite · determinism
  • 2 of 3 re-runs must reproduce

Repair — guard the input the proof blames

The certificate says ratio(0, 0) raised a division error, so the guard tests b == 0 rather than a generic None check. Each candidate is then applied and executed to earn its verdict. Nothing is written to your file — you get the diff and the decision.

  • Trigger-derived guards
  • Clamping for magnitude bugs
  • Verified · overfit · rejected
  • Never writes to your files

Record — keep the trigger, not a story about it

Opt in with --record and the failing call is stored in .buggy/findings.db. Later, buggy recheck re-runs every stored trigger and reports what is still failing, now fixed, regressed, or unreachable because the code moved. buggy export-tests turns them into pytest cases.

  • Opt-in, never automatic
  • Re-runnable triggers
  • Regressions exit non-zero for CI
  • Exports to pytest

What a certificate has to survive

A crash alone is not evidence. Three checks have to pass, and failing any one of them means nothing is reported.

01

Admissibility

The triggering input is re-checked against every precondition. A bug reached through an input you promised would never arrive is not your bug.

02

Soundness

The function is executed again in a fresh process and the result is re-evaluated. The violation has to still be there on a clean run.

03

Reproducibility

Three further executions, of which at least two must fail identically. A flake that cannot be reproduced never becomes a certificate.

Two failures it deliberately will not report. A non-finite result from non-finite arguments is IEEE 754 working as designed, so monthly(nan) returning nan is not a finding while ratio(0, 0) is. And TypeError from passing None is the caller's mistake, so it is ranked last and the search keeps going — which is why you get divide(x, 0) rather than divide(None, None).

A fix earns its verdict by running

A patch that special-cases the input which caught it passes every test you have and fails in production. Rather than score the shape of the edit, Buggy applies each candidate and asks four questions.

01

Does it parse?

A candidate that does not compile is rejected before anything else runs.

02

Does the trigger stop failing?

The exact proven call is re-executed against the patched function.

03

Did anything that worked break?

Every input that previously succeeded is replayed and compared.

04

Does it generalise?

Fresh inputs of the same shape are generated and run against the fix.

Three verdicts, each with its evidence. verified fixes the trigger, breaks nothing that worked, and handles similar inputs too. overfit fixes only the exact trigger. rejected does not parse, or breaks working inputs. There is no probability and no threshold — the report says what happened when the patch ran, for example "fixes the trigger, 37 working inputs unchanged, 2 of 2 similar inputs also fixed".
Why this replaced a classifier. The earlier implementation scored patches across a 66-dimensional feature vector and rejected anything above 0.5. On its own recorded runs it rejected all 21 candidates it ever produced, scoring the correct if people == 0: return 0.0 guard at 93% likely-overfit, with every score landing between 0.86 and 0.99. Executing the patch answers the same question without the calibration problem.

Then it checks whether the fix held

Recording a defect is easy. Knowing whether it came back is the part that usually gets skipped — and the only way to answer it honestly is to run the thing again.

record Keep the call, not a story

--record stores the exact failing call in .buggy/findings.db: the arguments, the rule it broke, the conditions it ran under. Opt-in, because a tool that inspects your code should not start writing files uninvited.

recheck Still failing, or fixed?

buggy recheck re-runs every stored trigger and reports each as still failing, now fixed, regressed, or unreachable because the code moved. Regressed means it was observed fixed and is failing again, which is the one worth acting on. The command exits non-zero when anything regressed, so it works unchanged as a CI step.

export Turn it into a test

buggy export-tests writes recorded defects out as pytest functions, so a proven defect becomes a regression test without being retyped.

What was left out, and why. An earlier design promoted findings into prose "lessons" and shared them across projects via a sanitised index in your home directory. That is gone: it wrote outside the project for a weak signal, and a trigger from another codebase cannot be re-run against yours, so none of its claims could be checked.

Three ways to drive it

Same core underneath all of them.

# what is in this file? parses only, runs nothing
buggy functions src/pricing.py

# prove one function, with conditions written in Python
buggy investigate apply_discount -f src/pricing.py \
  --pre 'price >= 0' --post 'result >= 0'

# propose fixes, each verified by execution
buggy repair apply_discount -f src/pricing.py

# machine-readable, for CI
buggy investigate apply_discount -f src/pricing.py --json

Conditions are Python expressions. Parameter names are in scope and postconditions also see result. A condition that cannot be evaluated is reported as a warning, never skipped silently. 

{
  "mcpServers": {
    "buggy": {
      "command": "/Users/you/.local/bin/buggy-mcp",
      "autoApprove": [
        "buggy_functions",
        "buggy_recall"
      ]
    }
  }
}

Tools exposed: buggy_functions, buggy_investigate, buggy_repair, buggy_scan, buggy_recall, buggy_recheck. Only the first and buggy_recall are auto-approved above: the other four import your module to prove a defect, which runs its top-level code, so you are asked first. 

from buggy.prove import investigate, Config

report = investigate(
    "src/pricing.py", "apply_discount",
    preconditions=["price >= 0", "percent_off >= 0"],
    postconditions=["result >= 0"],
    config=Config(max_executions=300, timeout=2.0),
)

# 'proven' | 'unconfirmed' | 'no_valid_input' | 'skipped'
print(report.status)

if report.certificate:
    print(report.certificate.rule)        # what it broke
    print(report.certificate.args)        # the failing input

Install

Python 3.10 or newer is the whole requirement. There is nothing to compile and nothing to download.

1

Add it

git clone https://github.com/himanshusaini-afk/buggy.git
cd buggy

python3 -m venv ~/.buggy-venv
~/.buggy-venv/bin/pip install -e .

The virtualenv keeps the tool from touching the environment of whatever project you point it at. Nothing is installed into your project.

2

Put it on your PATH

mkdir -p ~/.local/bin
ln -sf ~/.buggy-venv/bin/buggy     ~/.local/bin/buggy
ln -sf ~/.buggy-venv/bin/buggy-mcp ~/.local/bin/buggy-mcp

Symlinks rather than a venv path in your config, so the venv can be rebuilt without breaking anything downstream. Check ~/.local/bin is on your PATH.

3

Find a bug

buggy functions src/pricing.py
buggy investigate apply_discount -f src/pricing.py --post 'result >= 0'

Or skip installing entirely: PYTHONPATH=. python3 -m buggy.cli --help from the checkout.

Requirements

  • Python 3.10 or newer. That is the only requirement.
  • No dependencies. Standard library only, and none are planned for the core.
  • No Node, and no build step. Earlier versions of this project were written in TypeScript; that implementation was removed and is preserved at the ts-final tag.
  • Your code is really executed. See the warning below before pointing it at anything that touches the outside world.

What runs today

This is early software. Rather than let the diagrams imply otherwise, here is what works and what is deliberately absent.

Working and tested

  • Function and class inspection via ast, with a stated reason for anything skipped
  • Annotation-driven input generation, edge cases before randoms
  • A reusable worker process at about 0.015 ms per call, with timeout, kill-and-respawn and RLIMIT_CPU
  • Five oracles: timeout, crash, postcondition, non-finite, determinism
  • Propagation and type-confusion ranking, so the interesting failure is reported
  • Three-pillar certification: admissibility, soundness, reproducibility
  • Instance methods, with the receiver inferred from __init__ or pinned by hand
  • A Python specification language with a restricted evaluator
  • Repair with execution-verified verdicts
  • Recording, recheck, and pytest export
  • CLI, MCP server, and an importable API

Not here, on purpose

  • Any language but Python. A .ts file is refused, not guessed at
  • A sandbox. The boundary is an OS child process with CPU and file-size caps — there is no filesystem, network or syscall restriction
  • A hard memory cap on macOS. RLIMIT_AS cannot be lowered there, so limits are reported rather than assumed
  • Async functions. Refused with a reason; the worker has no event loop
  • Special methods. __init__, __add__ and the rest are refused — their calling conventions vary too much to guess
  • Defects needing several calls on one object. The receiver is rebuilt per call, which is what makes reproducibility sound
  • Cross-project memory and generated hooks or steering, both dropped for want of checkable evidence
  • MCP resources and prompts. The endpoints answer with empty lists so clients that probe them do not error
Side effects happen. Your functions are really executed, and for an instance method so is the constructor, with generated arguments. Running Buggy over its own source once left a stray SQLite file behind, because a generated argument reached a constructor that opens a database. Nothing is faked or mocked — that is what makes a finding reproducible, and also what makes this a real consideration. Inventory with buggy functions first, run it on a clean working tree, and do not point it at code you would not run.

Point it at your riskiest function.

If there is an input that breaks it, you will have the input — not a warning.
