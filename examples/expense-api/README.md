# Example: `expense-api` (Python)

A small Python expense-tracking module with **real, deliberate bugs**, plus a
runner that logs every phase of Buggy's pipeline. Use it to see exactly what the
tool does before pointing it at your own code.

Everything in `logs/` is the output of an actual run — no hand-written samples.

---

## 1. Run it

From the Buggy repo root, with `dist/` built:

```bash
npm run build
node examples/expense-api/run-buggy.mjs
```

Then read `logs/run.log` top to bottom.

**Expect about 8 minutes**, and note where the time goes — it is the opposite of
what you would guess:

| Function | Outcome | Time | Inputs tried |
|---|---|---|---|
| `split_expense` | bug proven | **2.7s** | 1 |
| `average_expense` | bug proven | **3.1s** | 1 |
| `budget_usage` | bug proven | **2.9s** | 1 |
| `apply_discount` | unconfirmed | 112s | 20 (budget exhausted) |
| `monthly_average` | unconfirmed | 98s | 20 |
| `remaining_budget` | unconfirmed | 103s | 20 |
| `clamp_percent` | unconfirmed | 173s | 20 |

Bugs are found almost instantly; **clean code is what costs you**, because a
function with no reachable failure has to burn the entire search budget before it
can say "unconfirmed". Each attempt spawns a real `python` process, so the budget
directly sets the wall-clock cost. In practice you point Buggy at a handful of
risky functions, not your whole codebase.

| File | Contains |

you nothing about false positives.

## 4. Using it on your own project

```bash
cd /path/to/your/project
buggy init                 # detects language, asks a few questions
buggy analyze src/thing.py # parse + list functions
buggy investigate my_func --file src/thing.py
```

For results you can trust, supply a specification (see §6) via the MCP tool or
the API rather than the bare CLI — the reason is in §8.

## 5. Every CLI option

### Commands

| Command | Purpose |
|---|---|
| `buggy init` | Set up the project. Detects language, asks 5 questions, writes `.debugger.yaml` + `.debugger/` |
| `buggy analyze <file>` | Parse a file: node count, syntax errors, functions found |
| `buggy investigate <fn> --file <path>` | Run the full pipeline on one function |
| `buggy status <id>` | Status of an investigation |
| `buggy halt <id>` | Stop a running investigation, keeping partial results |

### Flags

| Flag | Applies to | Effect |
|---|---|---|
| `--yes`, `-y` | `init` | Accept detected defaults, no prompts |
| `--language`, `-l` | `init` | Force `typescript` \| `javascript` \| `python` |
| `--force` | `init` | Overwrite an existing `.debugger.yaml` |
| `--file`, `-f` | `investigate` | The file containing the function |
| `--json` | all | Machine-readable output; never prompts |
| `--verbose` | all | Extra detail — on `investigate` this prints patch diffs |
| `--help`, `-h` | all | Usage |

Prompts are skipped automatically when stdin isn't a terminal, so `init` is safe
in CI.

### The `init` questions

| Question | Options | Default |
|---|---|---|
| Primary language | typescript / javascript / python | detected from your files |
| Search effort | quick (30) / balanced (100) / thorough (300) | balanced |
| Per-function timeout | 1–300 seconds | 60 |
| Memory scope | local / team / global / layered | layered |
| Add `.debugger/` to `.gitignore` | yes / no | yes |

## 6. Every config option

```yaml
language: python              # typescript | javascript | python
                              # Selects BOTH the grammar and the execution runtime.

parser:
  command: tree-sitter-python # grammar for the language
  grammar_path: ./custom.wasm # optional custom grammar

lsp:
  command: pylsp              # optional, improves symbol resolution
  initialization_options: {}

sandbox:
  runtime: python             # python | node
  memory_limit_mb: 512        # 64–8192
  timeout_seconds: 60         # 1–300
  egress_policy: deny         # deny | allow_host_only

oracles:                      # always-on failure detectors
  timeout_threshold_seconds: 5  # longer than this counts as a hang
  crash_detection: true         # uncaught exceptions
  overflow_detection: true      # NaN / Infinity / overflow
  determinism_check_count: 2    # re-runs to confirm the result is stable

probe:
  search_budget: 20           # inputs to try before giving up
  max_refinement_iterations: 5

watchlist:
  enabled: true
  scope: team                 # local | team | global | layered
```

### Writing specifications

Pre/postconditions are **JavaScript expressions even for Python targets**.
`result` is the return value and parameter names are in scope.

| Pattern | Add |
|---|---|
| Division | `!isNaN(result)`, `isFinite(result)` |
| Money / counts | `result >= 0` |
| Bounded values | `result >= 0 && result <= 100` |
| Collections | precondition on length |

**Preconditions are the biggest lever on signal quality.** Without
`Number.isFinite(x)` bounds the fuzzer injects `NaN`, and every arithmetic
function returns `NaN` for a `NaN` input — so everything looks broken and nothing
is informative. This runner declares finite ranges for exactly that reason.

## 7. Reading the result

| Status | Meaning | What to do |
|---|---|---|
| `confirmed_and_repaired` | Bug proven, and a fix passed the overfit check | Review the diff, then apply it |
| `confirmed_no_repair` | Bug proven, every candidate fix rejected as overfit | Write the guard yourself using the trigger |
| `unconfirmed` | No failing input found **within budget** | Not proof of safety. Raise `search_budget` or tighten the spec |
| `halted` | Stopped early | Check the error in the report |

A proven bug is always a true positive — it was re-executed and observed to fail.
The certificate records three checks: **admissible** (the input satisfies your
preconditions), **sound** (re-running really does violate the rule), and
**unique** (the failure belongs to this function).

Buggy never edits your source. Patches come back as data; applying them is your
call.

## 8. Honest limits

- **Specs still beat no specs.** The bare CLI now reads the real parameter list
  off the CST, so `buggy investigate split_expense --file src/expenses.py` finds
  the genuine `[0, 0]` → `ZeroDivisionError` with no setup. What it *can't* infer
  is intent: without postconditions you get the always-on oracles (crashes,
  timeouts, NaN/Infinity, non-determinism) but not rules like `result >= 0`. For
  unannotated Python parameters the type is `unknown`, so the fuzzer uses a
  generic value set rather than a targeted one. Supply a spec, as
  `run-buggy.mjs` does, when you care about a specific property.
- **Clean functions are the slow ones.** A bug is usually found on the first
  input; a clean function must exhaust the whole budget. That asymmetry is why
  this example lowers `search_budget` to 20 — see the comment in `.debugger.yaml`.
- **`unconfirmed` is not "safe."** It means nothing was found in the budget given.
- **Correct fixes may still be rejected.** The classifier scores patches by AST
  shape, and a minimal guard currently lands just above the 0.5 threshold
  (~0.51 for TypeScript, ~0.60 for Python). Expect to apply guards by hand today;
  the reliable value is the proof and the exact trigger. In this run every
  candidate was rejected — see `logs/patches.md`, where the **correct** fix
  (`if people == 0: return 0.0`) sits at 93%. The patches themselves are sound
  Python; it is the classifier's scoring that is too blunt to recognise a minimal
  guard.
- **Fuzzing is stochastic and misses combination bugs.** `apply_discount` has a
  real defect (`percent_off > 100` yields a negative price) but came back
  `unconfirmed`: triggering it needs a positive `price` **and** a `percent_off`
  above 100 in the *same* input, which 20 attempts didn't pair up. Single-value
  triggers like `0` or `[]` are caught reliably; combinations need a bigger budget.
- **The memory accumulates across runs.** Every investigation is recorded as an
  episode, so running twice doubles the episode count in `logs/watchlist.log`.
  That is the Watchlist working as intended. Delete `.debugger/` for a clean slate.
- **The sandbox is process-level, not a VM.** Functions run in a spawned
  `python`/`node` process that shares your filesystem and network. Fine for your
  own code; don't point it at untrusted third-party code expecting containment.

## 9. The fixes for these bugs

Using the proven triggers:

```python
# src/expenses.py
def split_expense(amount, people):
    if people == 0:
        return 0.0
    return amount / people

def average_expense(amounts):
    if len(amounts) == 0:
        return 0.0
    return sum(amounts) / len(amounts)

def apply_discount(price, percent_off):
    pct = max(0, min(100, percent_off))   # clamp to [0, 100]
    return price - price * (pct / 100)
```
```python
# src/budget.py
def budget_usage(spent, budget):
    if budget == 0:
        return 0.0
    return (spent / budget) * 100
```

This example intentionally keeps the **buggy** source so the run stays
reproducible. Apply the guards in a copy and re-run to watch each status flip to
`unconfirmed`.
